# The Core Engineering Reality & Metric Baselines

The propaganda‑forensics system, dubbed PROPAGIA in the source paper, processes a corpus of 2,646 French articles harvested from the Storm‑1516/CopyCop campaign disclosed by VIGINUM and INSIKT GROUP in 2025. Its counterpart, SIPA, serves as a human‑written baseline drawn from mainstream press of the same period. The forensic workflow begins with topic modeling using LDA, followed by vagueness scoring via a custom entropy‑based metric, sentiment analysis with a multilingual BERT variant, and source‑citation counting. Across these dimensions, PROPAGIA exhibits a 37% increase in vagueness, a 22% rise in subjectivity, and a 15% dip in citation density relative to SIPA. The system also harvested prompt‑instruction leaks from 50 of the 84 PROPAGIA‑hosting sites, revealing a ten‑point editorial specification that directly shapes the observed stylistic deviations.

Virgil, by contrast, does not generate content but provides an interactive navigation layer for explainability tools targeting transformer‑based language models. Its knowledge base indexes 112 distinct tools ranging from attention‑visualization suites like BertViz to gradient‑based saliency methods such as Integrated Gradients. Users launch Virgil via a lightweight Electron wrapper that queries a local SQLite catalog; the UI renders a force‑directed graph where node size correlates with community adoption metrics and edge weight reflects methodological compatibility. Telemetry collected during a two‑week user study showed an average session duration of 7.3 minutes, with 68% of participants successfully locating a tool that matched their explainability goal without external assistance.

Both systems share a reliance on containerized micro‑services. PROPAGIA decomposes into four services: ingestor, model‑wrapper, analyst, and reporter. The ingestor pulls raw articles via a Kafka topic at 1.2 Mbps, the model‑wrapper runs a fine‑tuned Llama 3‑8B checkpoint behind a TensorRT inference server, the analyst executes the forensic pipelines in a Dask cluster, and the reporter writes results to a PostgreSQL‑backed data lake. Virgil’s architecture is slimmer: a frontend service, a catalog service, and a plugin gateway that dynamically loads explainability modules as WebAssembly blobs. The frontend consumes ~200 MB of RAM, the catalog service ~150 MB, and each plugin isolates its own memory footprint, preventing a single greedy module from blowing the overall budget.

Field application of PROPAGIA appears in threat‑intel pipelines where analysts need to auto‑flag synthetic propaganda before it reaches social‑media moderation queues. Deployment on a Kubernetes cluster with three node pools (two spot, one on‑demand) yields a steady‑state throughput of 18 articles per second, with a 99th‑percentile latency of 842.3 ms as observed in the hook. Virgil finds its home in ML‑ops teams that must justify model decisions to regulators; integrating Virgil into a model‑card generation workflow cuts the average time to produce an explainability appendix from 45 minutes to 12 minutes, according to internal metrics logged at a Fortune 500 finance firm.



## Granular System Breakdown & Architectural Trade-offs

Diving deeper, the propaganda‑forensics pipeline’s ingestor uses a custom Avro serializer to compress raw HTML into 45 KB chunks, reducing network pressure on the Kafka broker. The model‑wrapper leverages TensorRT’s int8 calibration to shrink the Llama 3‑8B footprint from 16 GB to 5.2 GB VRAM, enabling deployment on a single T4 GPU. However, the int8 quantization introduces a 3.4 % drop in perplexity, which the analyst stage compensates for by ensembling three prompt variations and taking a majority vote on detected persuasion tags. This ensemble adds roughly 120 ms of latency per article but boosts F1‑score on the vagueness detection task from 0.71 to 0.83.

The analyst service runs the forensic steps as a Dask graph with four stages: topic modeling (LDA with 50 topics), vagueness scoring (Shannon entropy over token‑level POS tags), sentiment (XLM‑RoBERTa fine‑tuned on a multilingual propaganda corpus), and citation extraction (regex‑based lookup against CrossRef). Each stage is allocated a dedicated worker pool; the vagueness scorer is the most CPU‑intensive, consuming 62 % of the total CPU cycles measured via perf. To mitigate lock contention in the memory allocator, the team switched from glibc’s malloc to jemalloc with `lg_dirty_mult=3`, reducing allocator stalls from 8.7 % to 1.2 % under load.

Virgil’s catalog service stores tool metadata as JSON‑Lines files indexed by a SQLite FTS5 table. The search latency averages 9.4 ms for a fuzzy match over 112 entries, well within the UI’s 50 ms frame budget. Plugins are sandboxed via WASI; each plugin receives a 128 MiB linear memory cap enforced by the runtime. This isolation prevents a rogue gradient‑visualization module from leaking memory into the catalog service, a problem that plagued earlier versions where a single plugin’s memory leak caused OOM kills after ~4 hours of continuous use. The plugin gateway also implements a lazy‑loading strategy: only the UI‑requested tool’s WASM blob is fetched, cutting initial bundle size from 3.2 MB to 480 KB.

From a reliability standpoint, PROPAGIA’s reporter service writes to PostgreSQL using a connection pool of 20 connections. Under burst traffic (simulated via Locust at 150 rps), the pool exhibited occasional exhaustion, leading to `pq: sorry, too many clients already` errors. The fix involved introducing a bounded queue (size 50) ahead of the pool and applying exponential back‑off on retry attempts, which dropped error rates from 4.3 % to 0.1 %. Virgil’s frontend, built with React and Redux‑Toolkit, suffered from unnecessary re‑renders when the plugin list updated; switching to `useMemo` for the filtered tool list cut render time by 62 % during heavy plugin‑search sessions.

Cost analysis reveals nuanced trade‑offs. PROPAGIA’s GPU‑centric workload incurs a hourly charge of $0.52 for the T4 instance, plus $0.18 for the Kafka broker and $0.09 for the PostgreSQL‑managed service, totaling roughly $0.79/hour. At 18 articles per second, this translates to $0.04 per 1,000 articles, aligning with the $14.22/day figure when running continuously. Virgil’s CPU‑only deployment runs on two c5.large instances ($0.085/hour each) plus a managed Redis cache for session storage ($0.02/hour), yielding $0.19/hour. Over a month, the operational expense difference amounts to roughly $430 in favor of Virgil, though the value proposition differs: PROPAGIA delivers automated detection, whereas Virgil delivers human‑in‑the‑loop explainability.

Security considerations also diverge. PROPAGIA’s model‑wrapper exposes a gRPC endpoint for inference; hardening involved enabling mutual TLS and injecting a JWT‑based token scoped to the `propaganda:analyze` role. A penetration test uncovered a potential side‑channel via timing variations in the int8 quantizer; adding constant‑time padding to the elimination tree reduced variance from 214 ns to 12 ns. Virgil’s plugin gateway validates WASM blobs against a SHA‑256 whitelist before loading; any mismatch triggers a sandbox termination and an audit log entry. The gateway also enforces a strict CSP that blocks inline scripts, mitigating XSS risks introduced by community‑contributed plugins.

Scalability paths differ as well. To double PROPAGIA’s throughput, the team horizontally scaled the ingestor and model‑wrapper services, adding two additional Kafka partitions and spinning up two more T4 nodes. The analyst stage, however, became the new bottleneck; mitigating this required switching from LDA to an online variational Bayes implementation that processes documents in mini‑batches of 64, cutting per‑article CPU time from 23 ms to 15 ms. Virgil’s scalability is largely horizontal at the plugin level: new explainability techniques can be dropped into the plugin directory without touching core services, and the catalog service automatically re‑indexes upon file system events via inotify.

Operational observability shows both stacks emitting OpenTelemetry spans. PROPAGIA’s trace ID propagation spans the ingestor → model‑wrapper → analyst → reporter chain, with an average span duration of 842.3 ms matching the hook’s latency spike. Virgil’s trace captures the UI interaction → plugin gateway → plugin execution → result render path, averaging 210 ms from click to visualisation. Alerting policies are set on the 99th‑percentile latency: PROPAGIA triggers at >1 second, Virgil at >350 ms. Both systems feed alerts into a shared PagerDuty service, ensuring cross‑team visibility.

In practice, choosing between these tools hinges on the operational goal. If the priority is early detection of synthetic influence campaigns—where speed, recall, and low false‑positive rates protect downstream moderation—P​ROPAGIA offers a purpose‑built, albeit heavier, stack. If the aim is to empower model developers, auditors, or regulatory bodies with interpretable insights into transformer behavior, Virgil provides a lightweight, extensible dashboard that trades raw detection power for navigational clarity. Both benefit from the same foundational cloud‑native practices: container immutability, observability‑first design, and bounded resource allocation, which keep the systems running smoothly even when the logs start screaming with p99 latency spikes at 842.3 ms.

Gotchas & Risks emerge when the assumptions underlying each architecture shift. For PROPAGIA, reliance on a specific Llama 3‑8B checkpoint creates a version‑lock risk; updating the base model requires re‑quantization and re‑validation of the int8 pipeline, a process that can take two engineering weeks. Additionally, the forensic vagueness metric assumes a stable distribution of French linguistic features; a shift toward code‑mixed slang could degrade accuracy, necessitating periodic retraining of the sentiment model. For Virgil, the principal risk lies in plugin compatibility: as the explainability ecosystem evolves, older WASM plugins may fall out of sync with the host’s ABI, leading to silent failures. Mitigating this requires a version‑contract enforcement step in the plugin gateway’s load routine, which adds ~3 ms of overhead per plugin load. Finally, both systems share a common exposure to kernel‑level memory allocator bugs; staying on a recent glibc or jemalloc release and routinely running `malloc_benchmark` helps catch regressions before they manifest as OOM panics in production.

While the Virgil pipeline exhibited a marginally higher resident set size of roughly 2.3 GB under the same 1,000‑connection benchmark, its p99 latency remained more stable at 618 ms, thanks to a lock‑free arena allocator and a dedicated explainability worker pool that isolates heavy‑weight SHAP computations from the ingestion path. This divergence in resource‑latency trade‑offs sets the stage for a deeper look at how each system behaves in production‑grade telemetry, where failure modes are not just statistical outliers but operational hazards that can cascade across downstream analytics pipelines.
