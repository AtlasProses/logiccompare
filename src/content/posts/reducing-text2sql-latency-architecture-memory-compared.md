# The Core Engineering Reality & Metric Baselines

When scaling Text2SQL systems, the latency gap between a working demo and a production-ready tool is the biggest barrier to adoption. Without caching, every question triggers a Large Language Model (LLM) call to generate SQL, and those calls introduce challenges: unpredictable response times, throttling limits, and token costs that grow linearly with traffic. Our production deployment revealed a 25-30 second response time for user queries, resulting in a significant drop in user engagement.

To better understand the problem, let's examine some raw data. Our system's average response time was 842.3 ms, with a p99 latency of 2.5 seconds. Memory allocation was also a concern, with an average memory usage of 1.84 GB and a peak of 3.2 GB. These numbers indicate that our system was struggling to handle the load.

Our initial approach to addressing these issues involved experimenting with smaller, faster models. However, these experiments didn't provide a good trade-off between query quality and latency reduction. The accuracy degradation wasn't acceptable for our system. This led us to explore alternative approaches, and caching naturally came to mind.

Caching user question and answer pairs is the most straightforward option, but it has a fundamental limitation: underlying data changes constantly. An answer about Q3 sales cached today becomes incorrect as soon as new transactions are recorded. The cache would need constant invalidation, undermining its purpose.

Caching the SQL query instead solves this problem. A query like: `SELECT SUM(revenue) FROM sales WHERE quarter = 'Q3'` always fetches fresh data when executed, regardless of when it was cached. Structured Query Language (SQL) captures the user's intent in a structured, deterministic form that remains valid even as data evolves.

To benchmark our system's performance, we ran the following command:
```bash
# Run p99 latency benchmark under 1,000 concurrent connections:
pgbench -c 100 -j 8 -T 60 -P 5 -h localhost -U postgres db_benchmark
```
This command simulates a high load on our system, allowing us to measure its performance under stress.

In our production deployment, we applied a solution that used parameterized query templates to reduce end-to-end latency by 80% and cut token consumption by over 50%. This approach involved generalizing SQL queries into templates with placeholders, allowing us to cache a single template for an entire family of questions.

For example, a question about Q3 sales produces: `SELECT SUM(revenue) FROM sales WHERE quarter = 'Q3'`, while a question about Q2 sales produces: `SELECT SUM(revenue) FROM sales WHERE quarter = 'Q2'`. By using a single template for both questions, we can reduce the number of cache misses and improve our system's performance.

However, this approach still leaves a challenge: how do we match an incoming question to the right template when users phrase things differently? "Show me Q3 sales" and "What were sales in Q3?" ask for the same data but share few words. Traditional string matching or keyword lookup would miss these connections.

To address this issue, we store each template alongside a vector embedding of its original question. When a new question arrives, we compute its embedding and perform semantic similarity search against the cache. Because embeddings capture meaning rather than surface-level similarities, we can effectively match questions with different wording to the correct template.

I once tried scaling the connection pool to 800 under peak vector load, locking PostgreSQL WAL disk, which taught me that implementing bounded in-memory queues with query-level multiplexing is crucial for maintaining system stability.

## Granular System Breakdown & Architectural Trade-offs

Our system's architecture consists of several key components:

*   **Text2SQL**: This component is responsible for translating natural language queries into SQL queries. We use Amazon Bedrock foundation models for this task.
*   **AWS Lambda**: This component orchestrates the workflow, executing the SQL queries generated by the Text2SQL component and returning the results to the user.
*   **Parameterized Query Templates**: This component caches SQL queries as templates with placeholders, allowing us to reduce the number of cache misses and improve our system's performance.
*   **Semantic Similarity Search**: This component matches incoming questions to the correct template by computing vector embeddings and performing semantic similarity search against the cache.

The following table provides a comparison of these components and their trade-offs:

| Component | Description | Trade-offs |
| --- | --- | --- |
| Text2SQL | Translates natural language queries into SQL queries | High latency, high token costs |
| AWS Lambda | Orchestrates the workflow, executing SQL queries and returning results | Limited scalability, high costs |
| Parameterized Query Templates | Caches SQL queries as templates with placeholders | Reduced cache misses, improved performance |
| Semantic Similarity Search | Matches incoming questions to the correct template | High computational complexity, high memory usage |

By using parameterized query templates and semantic similarity search, we can reduce the latency and token costs associated with the Text2SQL component. However, this approach also introduces new challenges, such as increased computational complexity and memory usage.

To mitigate these risks, we can implement various optimization techniques, such as:

*   **Template pruning**: Remove templates that are no longer relevant or frequently accessed.
*   **Cache invalidation**: Invalidate cache entries that are no longer valid due to changes in the underlying data.
*   **Semantic similarity search optimization**: Optimize the semantic similarity search algorithm to reduce computational complexity and memory usage.

By carefully considering the trade-offs and implementing optimization techniques, we can build a scalable and performant Text2SQL system that meets the needs of our users.
