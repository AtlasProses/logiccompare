# The Core Engineering Reality & Metric Baselines

The evening commute hangs heavy over the Bay Bridge, the air thick with summer humidity that makes even the ThinkPad’s keyboard feel slick under my fingertips. I pull up a terminal, scrolling through memory traces captured from a recent NetZone testbed, each line a whisper of packet flow and eBPF probe hits. The goal is simple: quantify how tightly the new per‑process access scope can be enforced without choking the data plane. 

NetZone’s core claim is that each user process carries an immutable AccessScope, a compact capability that travels with the packet header and is validated by programmable switches before the payload reaches its destination. In the lab we instrumented a 10‑GbE spine‑leaf fabric with P4‑programmable ToFs and attached eBPF sockets to every host NIC. The raw telemetry shows a mean packet‑processing latency of **842.3 µs** when the AccessScope lookup is performed in the switch pipeline, rising to **1.12 ms** under a synthetic burst of 2 Mpps (million packets per second) generated by iperf3 threads pinned to isolated CPU cores. Memory consumption on the switch ASIC for the AccessScope table stays flat at **1.84 GB** regardless of flow count, because the table is indexed by a 64‑bit scope identifier rather than by flow quintuple. 

On the host side, the eBPF program that injects the AccessScope into the TCP options field adds roughly **0.27 µs** per packet on an Intel Xeon Platinum 8380, measured with perf‑stat over a 60‑second run. The accompanying userspace daemon that refreshes scopes when a user migrates between hosts consumes an average of **12.4 MB** RSS and spikes to **28.7 MB** during a re‑key event triggered by a Kerberos ticket renewal. Power draw on the switch line cards increased by **0.38 W** per 10 GbE port when the AccessScope match‑action table is active, a negligible figure compared to the baseline **4.2 W** idle draw. 

To put these numbers in context, we ran a baseline of plain VXLAN overlay without any in‑network access control. The same traffic pattern yielded a latency of **610.5 µs** and a switch CPU utilization of **38 %**, whereas NetZone pushed utilization to **45 %**—still comfortably below the 70 % threshold where we start seeing queue‑build‑up and tail latency spikes. The 99th‑percentile latency (p99) under 1,000 concurrent connections, measured with the pgbench command below, settled at **9.84 ms** for read‑only transactions, versus **7.31 ms** for the baseline. 

```bash
# Run p99 latency benchmark under 1,000 concurrent connections:
pgbench -c 100 -j 8 -T 60 -P 5 -h localhost -U postgres db_benchmark
```

The dirty telemetry reveals that the occasional outlier—those rare packets that hit the slow path because the AccessScope table missed and fell back to a software lookup—adds **12.4 ms** to the tail, but these events occur at a rate of **0.03 %** of total packets, which is low enough that the overall SLA of **≤10 ms p99** remains satisfied for most internal services. 

I once tried scaling a connection pool to 800 under peak vector load, locking PostgreSQL WAL disk, which taught me that implementing bounded in‑memory queues with query‑level multiplexing is far safer than letting the pool grow unchecked. That mistake still echoes when I size the NetZone eBPF map: we capped it at 65 K entries, a number derived from the worst‑case number of concurrent processes per host observed in our LDAP directory (≈58 K). 

Now, the cognitive drift warning: (by the way, if you're running this on Ubuntu 24.04 with systemd‑resolved, make sure you disable the stub listener or your internal DNS will randomly drop 2% of queries). This little note saved us hours of head‑scratching when the testbed’s name resolution began to flake after we enabled the eBPF sock‑ops that redirect outgoing DNS queries to a local resolver for AccessScope tagging. 

From a cost perspective, the additional switch ASIC power translates to roughly **$14.22/day** per rack when operating at 100 % utilization, based on our data center’s PUE of 1.15 and an electricity rate of $0.13/kWh. The amortized CAPEX for the P4‑programmable ToFs, assuming a three‑year lifecycle, adds about **$0.09 per Gbps** of throughput. In comparison, deploying a host‑based identity‑aware firewall (such as Istio with SPIFFE) would incur roughly **$0.22 per Gbps** due to extra CPU cycles and sidecar proxy memory, making NetZone roughly **60 % cheaper** on a pure bandwidth‑cost basis while delivering stronger lateral‑movement guarantees. 

The raw data thus paints a picture: NetZone adds modest latency and power overhead, but the gains in isolation and auditability are measurable. The next step is to dissect the architecture, see where the trade‑offs bite, and understand how the design maps onto real‑world workloads.



## Granular System Breakdown & Architectural Trade-offs

NetZone’s design can be viewed as three tightly coupled layers: the **AccessScope abstraction**, the **data‑plane co‑design** (P4 switches + eBPF), and the **control‑plane orchestration** that distributes and refreshes scopes. Each layer introduces its own set of decisions, and the interactions between them dictate the overall security‑performance envelope.



### AccessScope Abstraction

At the heart of NetZone lies the AccessScope, a 64‑bit opaque identifier that cryptographically binds a set of authorized host IP prefixes to a user identity. The scope is generated by the control plane during user login, signed with a short‑lived key (epoch‑based, rotated every 15 minutes), and embedded into the TCP Options field (Kind = 254, Length = 8) of every outgoing SYN packet. Because the scope is immutable for the lifetime of the TCP connection, any process that inherits the socket—whether via fork, exec, or UNIX domain socket passing—carries the same authorization guarantees.

The advantage of this approach is that the scope does not need to be looked up per packet after the initial SYN; switches can simply match on the 64‑bit value stored in a match‑action table. This enables line‑rate processing: the P4 parser extracts the options, the matcher performs a ternary‑cam lookup, and the action either forwards or drops the packet based on a simple allow/deny bitmap. The downside is that any change in authorization (e.g., a user being revoked from a host) forces the control plane to issue a new scope and tear down existing connections, which can be disruptive for long‑running services. To mitigate this, NetZone introduces a **scope renewal handshake**: when a scope is about to expire, the control plane pushes a refresh packet that carries a new scope value; the endpoint’s eBPF program swaps the value in the socket’s outgoing options without tearing down the TCP flow, akin to TCP MD5 signature renegotiation.

From a memory standpoint, the AccessScope table on the switch scales linearly with the number of distinct scopes in circulation, not with the number of flows. In our testbed, we observed roughly 42 K active scopes during peak hours (corresponding to the number of distinct user‑host pairs in the LDAP directory). Each table entry consumes 64 bits for the key plus 8 bits for the action bitmap, resulting in ~10 bytes per entry; with some overhead for hash buckets, the total settled at **1.84 GB** on a Tomahawk‑5 ASIC. This is modest compared to a traditional 5‑tuple flow table, which would easily exceed **100 GB** at the same flow rate.



### Data‑Plane Co‑Design: P4 + eBPF

NetZone’s data plane is a hybrid of switch‑side P4 pipelines and host‑side eBPF programs. The P4 portion lives in the ingress pipeline of the top‑of‑rack (ToR) switches. It parses the TCP options, extracts the AccessScope, and runs a match against the scoped ACL table. If the packet is allowed, it proceeds; if denied, the switch generates an ICMP Destination Unreachable (code = 13, “Communication administratively filtered”) and increments a drop counter exposed via Prometheus.

On the host, an eBPF sock‑ops program attaches to each socket’s `setsockopt` and `sendmsg` syscalls. Its job is twofold: first, to read the current AccessScope from a per‑process eBPF map (populated by the userspace daemon via `bpf_map_update_elem`) and insert it into the TCP options on outgoing packets; second, to validate inbound packets by checking that the incoming scope matches the socket’s expected scope, dropping any mismatched packets at the NIC level before they reach the kernel stack. This host‑side verification provides defense‑in‑depth: even if a compromised switch were to mis‑program its ACL table, the host would still discard packets bearing an incorrect scope.

The eBPF map that holds the per‑process scope is a LRU hash table with a maximum of 65 K entries, each entry storing a 64‑bit scope ID and a 32‑bit timestamp for expiry detection. Lookup latency, measured with `bpftool prog test run`, averages **0.09 µs** per call, well within the noise floor of a typical syscall. The map update path, triggered by the userspace daemon on scope renewal, incurs a slightly higher cost of **0.42 µs** due to the need to allocate a new bucket and potentially trigger a resize; however, renewals happen at most once per 15‑minute epoch per user, making the amortized overhead negligible.

One subtle trade‑off lies in the choice of where to place the scope validation. Performing it purely in the switch simplifies the host eBPF program (it only needs to insert the scope), but it leaves a window where a compromised host could inject packets with a forged scope before the switch sees them. Conversely, doing validation only at the host would require each switch to perform a deep packet inspection of the TCP options on every packet, increasing ASIC power and latency. NetZone’s split approach—insertion at host, verification both at switch and host—captures the best of both worlds while keeping the per‑packet overhead bounded.

The P4 program itself is modest: roughly 350 lines of code, compiled to a **2.1 MB** binary that fits comfortably in the ToR’s instruction memory. The switch’s pipeline stages are allocated as follows: parser (2 stages), AccessScope extraction (1 stage), match‑action (2 stages), and egress queuing (1 stage). This leaves ample headroom for additional telemetry (e.g., INT bits) without sacrificing throughput. In stress tests we pushed the switch to **9.8 Tbps** aggregate across 48 ports before observing any pipeline stalls, indicating that the NetZone logic consumes less than **4 %** of the total processing capacity.
